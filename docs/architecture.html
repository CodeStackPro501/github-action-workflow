GitHub Actions CI/CD

A visual guide to how CI pipelines work — concepts, workflow files, and code, all in one place.

⚡ What is CI/CD?

CI — Continuous Integration

Every time you push code, a pipeline automatically checks for errors, runs tests, and verifies formatting. Bugs are caught instantly — before anyone else is affected.

CD — Continuous Deployment

After CI passes, the code is automatically packaged and sent to a server. No manual steps, no "I forgot to deploy" moments.

🛡️ Without CI/CD vs With GitHub Actions

Without CI/CD
  • Tests run only when you remember
  • Broken code reaches production
  • Manual server login every deployment
  • Passwords typed in terminal — no security
  • No record of who deployed what
With GitHub Actions
  • Tests run automatically on every push
  • Failing tests block the pipeline
  • Deploy happens automatically after tests pass
  • Secrets injected securely — never in logs
  • Full audit: who pushed, which commit, what result

🧩 GitHub Actions — Key Concepts

Every keyword explained in plain English, with a simple example.

Keyword What it means (simple) Example from this project
Workflow The main automation file. Think of it as a recipe — it says what should happen and when. One repo can have many workflows. 01-ci-pipeline.yml
on: Decides when the workflow starts. You can set it to fire on a push, on a pull request, on a schedule, or manually. Without this, nothing runs. on: push pull_request
jobs: A workflow has one or more jobs — each job is a separate unit of work that runs on its own machine. Jobs can run at the same time or one after another. lint test summary
runs-on: Which type of computer (runner) should run this job. GitHub provides free virtual machines — Ubuntu, Windows, or macOS. Most projects use ubuntu-latest. ubuntu-latest
steps: A job is made of steps — individual tasks that run one by one in order. Each step is either a shell command or a pre-built Action. If one step fails, the next steps are skipped. Checkout → Install → Lint → Test
uses: Use a pre-built Action instead of writing the code yourself. GitHub Marketplace has thousands of ready Actions. Like installing an npm package — but for your pipeline. actions/checkout@v4
needs: Makes one job wait for another to finish first. The current job only starts if the listed job passed. Test job needs: lint — so tests won't run if linting fails. needs: lint
strategy.matrix: Run the same job multiple times with different values — at the same time. Great for testing across multiple Node.js versions in parallel. One config → three simultaneous jobs. node: [18, 20, 22]
concurrency: Controls what happens when two runs start at the same time. With cancel-in-progress: true, the older run is cancelled automatically. Saves runner minutes. No two runs overlap. cancel-in-progress: true
environment: Links a job to a named GitHub Environment (like "production"). Environments can have their own secrets and optional approval gates. Approval gate = someone must click "approve" before the job runs. environment: production
secrets.* Safe way to use passwords, API keys, and tokens. You store them in GitHub Settings — they are never visible in code or logs. Even if you accidentally write echo $SECRET, GitHub shows *** in logs. secrets.DEPLOY_TOKEN
$GITHUB_STEP_SUMMARY Write a Markdown report to the Actions dashboard. Every team member can see a clean summary — no need to dig through raw logs. Shows: which tests passed, which commit, who triggered it. CI Pipeline Report ✅
if: always() Run this step/job even if the previous one failed. Used on the Summary job so you always get a report — even on failure. Without this, a failed test would hide the summary. if: always()
fail-fast: false When using matrix, don't stop other jobs if one fails. Default behavior cancels all matrix jobs when one fails — this setting prevents that. You want to see ALL results, not just the first failure. fail-fast: false

⚙️ CI Workflow — Code Breakdown

Triggers — on:

Three ways this pipeline starts:

on:
  push:
    branches: [main]         # fires when you push to main
  pull_request:
    branches: [main]         # fires when a PR targets main
  workflow_dispatch:          # "Run workflow" button in GitHub UI

# If two pushes happen quickly, cancel the older run automatically
concurrency:
  group: ci-${{ github.ref }}
  cancel-in-progress: true

Job 1 — lint (syntax check)

Runs first. Checks if all JS files have valid syntax using Node's built-in checker — no extra tools needed.

lint:
  runs-on: ubuntu-latest
  steps:
    - uses: actions/checkout@v4           # download your code to the runner
    - uses: actions/setup-node@v4
      with:
        node-version: '20.x'
        cache: 'npm'                    # reuse node_modules from cache = faster
    - run: npm ci                       # clean install from package-lock.json
    - run: npm run lint                 # node --check app.js server.js
    - run: npm run format:check         # Prettier — is code style consistent?

Job 2 — test with Matrix (runs after lint)

Runs the same tests on Node 18, 20, and 22 — all at the same time. fail-fast: false means you see all results even if one fails.

test:
  needs: lint                      # only starts after lint passes ✅
  strategy:
    fail-fast: false               # don't cancel Node 22 if Node 18 fails
    matrix:
      node: ['18.x', '20.x', '22.x']  # 3 jobs run in parallel

  steps:
    - uses: actions/checkout@v4
    - uses: actions/setup-node@v4
      with:
        node-version: ${{ matrix.node }}  # each job uses a different version
    - run: npm ci
    - run: npm test

    # Upload coverage only once — from the Node 20 job
    - if: matrix.node == '20.x'
      uses: actions/upload-artifact@v4
      with:
        name: coverage-report
        path: coverage/
        retention-days: 14

Job 3 — summary (always runs)

if: always() means this job runs even if tests fail — so you always see a report in the Actions dashboard.

summary:
  needs: test
  if: always()                     # run even when test fails
  steps:
    - run: |
        echo "## CI Pipeline Report"  >> $GITHUB_STEP_SUMMARY
        echo "| Check | Status |"      >> $GITHUB_STEP_SUMMARY
        echo "| Lint  | ✅ Passed |"   >> $GITHUB_STEP_SUMMARY
        echo "| Tests | ✅ Passed |"   >> $GITHUB_STEP_SUMMARY

🆚 npm ci vs npm install

Always use npm ci in pipelines. Here's why:

Propertynpm installnpm ci
Lock fileMay update package-lock.jsonReads it, never changes it
SpeedSlower (resolves semver ranges)Faster (uses exact versions)
node_modulesUpdates existing folderDeletes and reinstalls clean
Use whenLocal developmentCI/CD pipelines ← always

🧪 Test Suite — tests/app.test.js

12 test cases — happy paths, edge cases, and error handling. The CI pipeline runs all of them on Node 18, 20, and 22 in parallel. If even one fails, the pipeline stops.

// Happy path — expected correct results
expect(body.status).toBe('UP');         // health endpoint works
expect(body.finalPrice).toBe(80);        // 20% off 100 = 80
expect(body.finalPrice).toBe(89.99);     // floating-point handled correctly
expect(body.finalPrice).toBe(0);         // 100% discount = free

// Error cases — should return 400 Bad Request
expect(status).toBe(400);               // string passed instead of number
expect(status).toBe(400);               // negative amount
expect(status).toBe(400);               // discount percent above 100

// 404 — route that does not exist
expect(status).toBe(404);

🔧 Use This Setup in Your Own Project

1
Create the workflow folder
Run mkdir -p .github/workflows in your project root. This is where all workflow files live.
2
Add a test script to package.json
GitHub Actions calls npm test — make sure it exits with a non-zero code when tests fail.
3
Copy 01-ci-pipeline.yml
Change the Node version matrix if your project has different requirements. Everything else works as-is.
4
Copy 03-pr-check.yml
This gives you automatic feedback on every Pull Request — no configuration needed.
5
Push and open the Actions tab on GitHub
Watch every job run in real time. Click on the Summary panel to see the Markdown report.
